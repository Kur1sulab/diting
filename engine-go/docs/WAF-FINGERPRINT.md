# WAF / bot 指纹作为资产属性（调研总纲 §3 P1）

## 1. 要解决的错

扫描链原先只判「通 / 不通 / 状态码」。WAF 返回 403、412、202 挑战页时，
`fingerprint` 打印「请求失败」、`verify` 记一条「有 HTTP 响应」就完事——
于是**被拦 = 不存在**。这是漏扫里最贵的系统性错误：目标明明活着，只是
站在门后被拦，报告上却写成「未发现资产」。

本模块把「前面有没有 WAF、什么牌子、有没有 bot 挑战」变成资产的**属性**，
供空境 Kara 选路：是绕、降速、换指纹，还是标注为需人工。

## 2. 设计约束

| 约束 | 实现 |
|---|---|
| 不发请求 | `waf.Detect(waf.Response) *waf.Attribute` 纯函数，输入是已抓到的响应快照 |
| 可离线回放 | 判定只依赖 `testdata/fixtures.json`，测试零网络 |
| 证据先于结论 | 没有 evidence 的候选一律淘汰；凑不出证据只能报 `unknown` 或不报 |
| 置信度诚实 | 置信度由强弱特征**计数**算出（`confidenceOf`），规则表不许自带置信度 |
| 不猜品牌 | 猜错品牌比报 `unknown` 更贵（Kara 会按错误品牌选错绕法） |

## 3. 判定模型

### 3.1 强 / 弱特征

- **强特征**：只可能来自该厂商——独家响应头（`cf-ray`、`x-iinfo`、`x-wa-info`）、
  独家 Cookie 前缀（`__cf_bm`、`visid_incap_`、`FSSBBIl1UgzbN7N`）、品牌文案。
- **弱特征**：共享的、可能来自别处——通用 403、LB 持久化 Cookie（`BIGipServer*`）、
  云厂商通用请求 ID、通用 JS 挑战标记。

### 3.2 置信度阶梯

| 强 | 弱 | 置信度 | 含义 |
|---|---|---|---|
| ≥2 | 任意 | `high` | 两个互不相关的强特征，几乎不可能是巧合 |
| 1 | ≥2 | `high` | 一强两弱互证 |
| 1 | 0–1 | `medium` | 品牌可信，**WAF 模块是否真的开启未确认** |
| 0 | ≥2 | `medium` | 多弱特征互证，没有独家特征 |
| 0 | 1 | `low` | 单一弱特征，只能当线索 |
| 0 | 0 | — | 不产生结论（返回 nil） |

> `medium` 及以下请理解为「设备/品牌大概率对」，**不要**当成「确定有 WAF 拦截」。

### 3.3 两条防误报闸门

1. **pageLike 门槛**：`200/201` 且正文 > 8KB 视为正常应用页面，正文特征全部不参与
   判定（技术博客里写「雷池」「ModSecurity」不该被判成 WAF）。例外：
   `river-security` / `geetest` / `dinjie` —— 它们的特征本来就注入在正常页面里。
2. **拦截页需要状态码背书**：通用兜底（`unknown`）要求「拦状态码（403/406/412/429/501/503）
   + 拦截页文案」同时成立。裸 `403 Forbidden`（nginx 默认页）不算。

## 5. JSON 契约（Kara 直接消费）

### 5.1 单资产属性（`subdomains_live.json` → `http.waf`）

```json
{
  "vendor": "cloudflare",
  "confidence": "high",
  "challenge": "js_challenge",
  "evidence": ["header:cf-ray=8f2a1b3c4d5e-LAX", "cookie:__cf_bm"]
}
```

- 四个键**恒在**，类型固定；`evidence` 永远是数组（空则 `[]`，不会是 `null`）。
- `http.waf` 为 `null` 表示「**已探活、无 WAF 证据**」；
  `http` 为 `{}` 表示「**未探活**」（DNS 可解析但没拿到响应）。
  这两种语义不同，消费方必须分开处理。

### 5.2 汇总（`waf.json`，verify / fingerprint 都产出同一形状）

```json
{
  "generated_at": "2026-11-23T22:27:01+08:00",
  "stats": {
    "alive": 12,
    "http_responded": 10,
    "waf_detected": 4,
    "by_vendor": {"cloudflare": 3, "unknown": 1},
    "by_confidence": {"high": 2, "low": 2},
    "by_challenge": {"js_challenge": 2, "none": 2}
  },
  "assets": [
    {"host": "a.example.com", "ips": ["203.0.113.10"], "scheme": "https",
     "status": 403, "final_url": "https://a.example.com/", "waf": { ... }}
  ]
}
```

- `assets` **只含判出 WAF 的资产**，按 `host` 排序（产物可 diff）。
- `alive` = 有 DNS 记录的资产数；`http_responded` = 拿到 HTTP 响应的资产数；
  `waf_detected` ⊂ `http_responded`。
- `by_vendor` / `by_confidence` / `by_challenge` 键就是第 4 节的枚举值，
  计数之和 = `waf_detected`。空集是 `{}` 不是 `null`。

### 5.3 Kara 选路建议映射

| `waf` 状态 | 建议 |
|---|---|
| `null`（探过、没 WAF） | 直连，正常节奏 |
| `vendor != unknown && confidence == high` | 按品牌走对应绕行策略；`js_challenge` 需先跑 JS 取 cookie |
| `confidence == medium` | 先小流量探测确认拦截行为，别按 `high` 的重策略上 |
| `vendor == unknown && confidence == low` | 有东西在拦但认不出，降速 + 观察状态码漂移，不做品牌定向绕过 |
| `challenge == captcha` | 脚本化成本最高，优先人工或换入口 |
| `http == {}`（未探活） | **不要**当成「没有 WAF」，这是未知 |

## 6. 已知边界（诚实清单）

- **AWS WAF 无专属响应头**：默认就是干巴巴的 403，只能靠 CloudFront/ALB 边缘特征
  间接定位，因此**上限 `medium`**。这是设计，不是缺陷。
- **裸 403 Forbidden 不判 WAF**：nginx/Apache 默认 403 页与 WAF 拦截页无法区分，
  宁可漏判也不误报（误报会让 Kara 对干净资产上重策略，代价更大）。
- **IPv6 / 非 HTTP 协议**：不覆盖。
- **WAF 只拦特定路径**（例如只拦 `/admin`）：本模块判的是「站点根响应」，
  路径级拦截需由 `paths` / `api` 模块的 403 归因补足。
- **JS 挑战需二次请求才能确认**：本模块只做单响应判定，不复现挑战。

## 7. 加一条规则

1. 在 `waf/rules.go` 的对应 `vendorRule` 里加 `Signal`，必须写 `Evidence`
   （形如 `header:xxx=%s` / `cookie:%s` / `body:%s`）并标 `Strong`。
2. 在 `waf/testdata/fixtures.json` 加**正例**；
   再加一条**误报陷阱**（同类干净响应必须返回 nil）。
3. `go test ./waf` —— `TestRuleTableSanity` 会拦住缺证据、枚举外厂商、
   cookie 前缀非小写这类手滑。
